## Evidence boundary

Diagnostic modules are `/tmp/pass5-writes/writes.cjs` and
`/tmp/pass5-writes/note-failures.cjs`. The coordinator owns the local runtime,
synthetic identity/group and sequential browser execution. Each module exports
`seed(api)` and `run(api)` and opens no server or browser itself.

The injected fault alters one selected outbound local Firestore
`Write/channel` request. The nine-case main run used
`currentDocument.updateTime = 1970-01-01T00:00:00.000000001Z`; the emulator
rejected its unsupported nanosecond precision with acknowledged
`INVALID_ARGUMENT: timestamp cannot have more than microseconds precision`.
This is a diagnostic transport mutation, not malformed data generated by the
application. It establishes handling of a real permanent write rejection; it
does not simulate a transient outage. The exact executed module is retained as
`writes-initial.cjs`.

The follow-up helper corrects the precision to
`1970-01-01T00:00:00.000001Z` to request a valid stale precondition. Its actual
UI/server results and acknowledgement limits are documented below. Target path,
original precondition and injected precondition are recorded. No application
service is replaced, no rules/configuration changes are made, and unaffected
transport proceeds normally. A UI error plus independent Admin SDK readback
establish each confirmed main result; pending/offline writes are not called
rejected writes.

Fixtures contain synthetic campaign content and prepared detections. Prepared
conversion uses the real UI and writers without an extraction request. Image
pixels are generated in the browser, uploaded to local Storage, and checked
through independent binary/document readbacks. Production data, credentials,

## WRITES-001 — Failed private-note Delete and Archive give no visible explanation

**Severity: Low. Confidence: High. Classification: new operation-feedback gap.**

**Source:** `src/pages/notes/NotePage.tsx:146–169` catches Archive/Delete failure
only with `console.error`; Delete always closes the dialog in `finally`.
Its dialog has no error state or rendered error message (`251–266`). The actual
mutation paths await their document operations at
`src/features/collaboration/notes/context/NoteContext.tsx:494–508`, so the
failure does reach this page handler. Existing failed-delete tests explicitly
expect the dialog to close (`src/pages/notes/__tests__/NotePage.test.tsx:564–575`).

**Concrete trigger and actual evidence:** Open an owned saved synthetic note and
confirm Delete. Inject one valid stale update-time precondition into that
note's delete request. The attempted operation settles with the confirmation
closed, the note still open, no visible failure reason in the complete captured
body, and no alert. Independent server readback confirms the full original
note remains active. Repeat on another owned note using Archive: the page stays
on that note without visible explanation and the server status remains active.
Both failures retain usable controls. Reopening Delete and confirming again
successfully removes its document and returns to `/notes`; pressing Archive
again successfully stores `status: archived` and returns to `/notes`.

The valid stale precondition is intended to produce `FAILED_PRECONDITION`.
The saved note snapshots do not include the exact error code/message because
these caught failures are logged only to browser console. They do establish
settlement and successful subsequent writes, rather than an indefinitely
pending transport operation. The nine-case main run separately preserves exact
acknowledged `INVALID_ARGUMENT` wording. Neither error is claimed to originate
naturally from unchanged app payloads.

**Expected and impact:** State that Delete/Archive failed, preserve the source
note and provide a clear retry. The source note is correctly retained, and retry
works, which limits severity to Low. The absent explanation leaves players
unsure whether to wait, repeat the action or reopen the note; closing a rejected
Delete confirmation especially obscures the result of a destructive action.
No unintended document deletion or permission bypass is claimed.

**Fix direction:** Use an operation-local action error on NotePage. Clear it
when starting/retrying the same action; on Delete failure, keep the confirmation
open with the error and reset its busy state. Show Archive failure by its
control or on the retained note. Navigate and close only after success. Keep
existing editor/draft content mounted and avoid feeding these operation errors
into the read gate.

**Focused validation:** Reject Delete and Archive independently; assert visible
failure reason, retained original document/content/status, settled enabled
retry controls and no premature navigation. Retry successfully, then assert
one intended delete/archive and `/notes` navigation. Also preserve Cancel and
healthy-action controls. The test that currently expects silent failed-delete
closure should follow the clarified recovery contract.

**Overlap:** FUNC-006 concerns chapter deletion's swallowed rejection and
persistently disabled retry; both note retries here remain usable. REACT-004
concerns autosave feedback in NoteEditor; this finding concerns explicit
NotePage actions with a separate catch/state owner. These are grouped as one
note-action cause, not two findings. They do not refile #1400's repaired NPC
form errors or #1051's repaired manual-save wrapper.
